A syntax linter sees tokens. It can tell you a key is misspelt; it cannot tell you that `requirePullRequestReviews: true` with `requiredApprovingReviewCount: 0` is a contradiction, because it does not know the values. A configuration language with constraints in the type can check one field's range; it cannot check a relationship between two resources.

Folding gives a rule the actual values, of every file in the build, before anything is emitted. So a rule can say "an owned org with no branch protection on its default branch" and be right, and it can say it in the editor, because the values are known without running anything. The check at the keystroke is the check in CI, over the same data, because the data is a function of the source.

## Two phases

Pre-synthesis rules run over the folded values, per file or across the build, before serialization. Post-synthesis rules run over the emitted artifact. Both are pure functions of their input: no execution, no environment, deterministic, which is what lets them run in an editor. A finding names a rule, a path into the value, and the source line it came from.

## Who has it today

chant's lexicons carry semantic lint rules for each target: the AWS lexicon knows which resource combinations are incoherent, the Kubernetes lexicon knows a container's hardening rules, and they run over folded values. forgejo-warden runs both phases without calling them that: its config loader validates the declared policy with the exact field path on a bad shape, and its guardrails (`removalDeltaCap`, `adminFloor`) run over the computed plan before any apply.

## Where the rule lives

Evaluability, "is this file data", is already specified as the `S-*` classifier and `F-Div-*`. The contract for semantic rules over values, `F-Rule-*`, is [issue #79](https://github.com/INTENTIUS/typescript-as-data/issues/79): the input a rule sees, its purity, its located findings, and the two phases. It is stated here as a forward reference, not as a claim.
